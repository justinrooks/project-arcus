# Installation enrollment

SkyAware consumes ArcusCore **0.7.0** for Signal installation enrollment. This development change must not be installed on devices or released until the compatible Signal v2 server from Signal #386 / PR #388 is deployed. Server deployment is a separate operation.

## Credential lifetime

`InstallationEnrollmentCoordinator.shared` owns enrollment for the three installation writers: location snapshots, preferences, and foreground activity. Public weather APIs do not use installation credentials. First foreground activity can enroll without an APNs token or notification permission; failed enrollment does not block public weather or cached UI.

The existing installation UUID must be durable before enrollment. A 32-byte cryptographically random secret is encoded as base64url without padding and saved in a device-only, after-first-unlock Keychain record before the first enrollment request. The record stores enrollment acknowledgment separately from credential existence. A lost response or failed acknowledgment persistence retries the same UUID and secret. HTTP 200 with the shared `status: accepted` acknowledgment establishes enrollment; subsequent foreground activations make no enrollment or credential-validation request.

A separate Keychain marker prevents credential loss from being interpreted as an eligible legacy first claim. Locked, corrupt, mismatched, or unavailable identity/credential state fails closed. HTTP 409 and protected-write HTTP 401 never generate replacement credentials or fall back to v1. Credential rotation and fresh-identity recovery are intentionally unavailable: notification continuity requires a separately approved recovery contract. Enrollment is bound to the configured HTTPS origin. The URLSession task delegate rejects every redirect for v2 installation POSTs, including aliases, to prevent forwarding credential bodies or bearer headers to another route, origin, or protocol.

Concurrent callers share one enrollment operation. Cancellation prevents a waiting caller's protected write; the shared claim retains ownership until it finishes, allowing its acknowledgment to be persisted and preventing a competing enrollment. A future caller can retry failed enrollment with the persisted credential.

## Pending uploads and consent ownership

The durable upload queue and its format remain unchanged. Rehydrated work, retries, and legacy source-value fallback all reach the authenticated v2 uploaders. The queued installation UUID must match the current durable identity; mismatches remain unsent rather than being reassigned. Payloads contain no credentials, and failed enrollment does not acknowledge or remove queued work.

SkyAware #794 resolves current subscription, Core Location authorization, APNs token and meso preference for each transfer, after enrollment and retry backoff. Revoked sharing or non-granted authorization discards pending location work, including forced uploads and legacy-source fallback; preference sync remains available without a location. An explicit subscription opt-out can restrict uploads while the defaults write catches up. Opt-in requires the setting provider to report enabled; an asynchronous enable callback cannot override a current disabled setting. An outstanding opt-out restriction clears only after a sync/upload observes defaults confirm disabled. A later enable then follows the setting provider. A rapid disable/enable whose intermediate disabled value is never observed remains conservatively disabled for that coordinator lifetime; Boolean callbacks alone cannot prove their user-intent order. Reopened queues use current settings rather than persisted consent metadata. The durable queue format is unchanged.

A request already handed to HTTP cannot be recalled. An old request can still commit after newer consent at Signal; client sequencing and these tests do not prove server commit order or recall of accepted APNs deliveries. Signal #379 owns that ordering correction. ArcusCore 0.7.0 is the contract baseline; adopting its v3 DTOs, revision authority and all v3 device routes belongs to SkyAware #798. Legacy v1 retirement remains Signal #387. No release or production validation is implied by this client change.

## Validation boundaries

Deterministic tests use synthetic HTTP seams, memory credential stores, isolated simulator Keychain services, and reopened UserDefaults upload queues. They establish client protocol, coordination, retry, and header behavior; they do not establish physical-device Keychain accessibility, production deployment, APNs delivery, or end-to-end consent ordering. Device acceptance must include ordinary app updates, locked-device background sends after first unlock, denied notification permission, and restart following lost enrollment acknowledgment after the compatible server is deployed.

### V3 consent and presence

SkyAware consumes ArcusCore 0.7.0 for v3 device writes. Enrollment remains `/v2/devices/enroll` with the same Keychain bearer credential. Preferences, location snapshots and foreground activity use v3 only; failures never select a legacy mutating endpoint. The legacy payload types used internally by the durable queue are preparation inputs, not v3 wire bodies. Historical queue consent remains nonauthoritative.

`InstallationConsentStore` reads the existing AppStorage defaults and current Core Location authorization. It stores one encoded installation UUID, positive Int64 revision and complete four-field snapshot in the existing defaults suite before permitting a v3 send. Only changed consent advances the revision. A separate Keychain marker is installed before the first transport handoff, so lost defaults after a lost acknowledgment cannot silently restart a promoted identity at revision 1. Corrupt state, identity mismatch, overflow, failed persistence or a server revision ahead of the local record defer device sync for explicit recovery; public weather remains independent.

Each location/activity admission first completes an authenticated current v3 preference sync, including after restart. Concurrent admissions may send equal-revision idempotent preferences; Signal owns atomic ordering and irreversible protocol promotion. Each response is compared with freshly reconciled local consent. Earlier or stale acknowledgments cannot replace current delivery ownership. APNs token and metadata changes do not advance consent revision. Initial consent and opt-out require neither a token nor a geographic observation. V3 location carries presence only, retains capturedAt ordering, and retains the queue's final sharing/authorization checks after admission waits. Ignored/stale presence acknowledgments discard the completed attempt without recording successful canonical replacement.

Release remains gated on deployed, validated Signal v3 and legacy-route compatibility/downgrade fencing. Unit/simulator evidence does not establish deployment, physical-device delivery, or recall of requests already handed to transport/APNs.
